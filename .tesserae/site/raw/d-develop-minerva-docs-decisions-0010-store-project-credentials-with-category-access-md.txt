# ADR 0010: Store encrypted project credentials with category-scoped access

Date: 2026-07-11  
Status: accepted

## Context

Teams need to store project logins, passwords, URLs, tokens, and notes. These values are more sensitive than ordinary project content. Project-wide RBAC alone cannot express that Production credentials are visible only to administrators and specifically selected members. The product previously excluded customer credentials and ADR 0002 deferred individual permission overrides.

## Decision

Add a project-scoped Credentials module with user-created, single-level categories. New projects have no predefined categories. Every credential belongs to exactly one active category.

Category read access is allow-only and is granted to project roles and/or individual active project members. Effective read access is the union of those grants. Individual grants are a credential-category capability, not general per-user RBAC overrides.

Every active Project Admin can read and administer every credential category. This access is implicit, cannot be removed by category grants, and is evaluated from stable permission codes rather than a localized role name. Project Admins manage categories, category grants, and credential records.

Secret values are encrypted by the application before PostgreSQL persistence with authenticated encryption and versioned keys held outside the database. Password list projections never include plaintext. ADR 0011 permits authorized list projections to include decrypted login values. Password reveal and copy use a dedicated authorized endpoint, and plaintext must not enter logs, errors, analytics, audit payloads, MCP responses, or generated indexes.

Credential operations are web-only in the first release. No credential MCP resource or tool is added.

Categories and credentials use recoverable archival rather than physical deletion. Grant changes, create/update/archive, and secret reveal/copy events are audited without secret values.

## Consequences

- Product scope expands to explicitly include encrypted project credentials.
- Authorization requires both project membership/permission checks and category access checks.
- Role and member grants need database constraints that keep all subjects inside the same project.
- Project Admin retains a non-removable recovery path to every category.
- Key rotation and operational recovery must be designed before production use.
- Explicit deny rules, nested categories, cross-project sharing, secret history, and MCP access remain deferred.
