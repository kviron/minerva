# Projects list and create UI design

**Status:** proposed  
**Date:** 2026-07-05

## Goal

Deliver the first usable Projects web slice: authenticated users can view projects in which they have an active membership, filter that list, create a project, and open a project. A super administrator receives a separate administration tab that lists every project in the system. Both views use the local shadcn-vue design system and follow Figma node `26:84`.

## Scope

This slice includes:

- a membership-scoped Projects application query and authenticated Nitro endpoint;
- a super-admin all-projects query and separately guarded Nitro endpoint;
- an authenticated project-creation endpoint backed by the existing atomic `createProject` service;
- a shared Projects client feature with strict response parsing, interaction state, filters, and reusable UI;
- the `/projects` page and an administration Projects tab;
- loading, failure, empty, filtered-empty, table, and create-dialog states;
- unit, PostgreSQL integration, and browser coverage.

Project settings, member management, role-matrix editing, archival actions, documents, credentials, and server-side pagination remain deferred.

## Server architecture and authorization

Transport handlers remain thin. Shared Projects application services own SQL projection and scope rules.

### Member project list

`GET /api/projects` requires a real active session. It derives the user UUID on the server and returns projects joined through that user's active membership. The endpoint never accepts a user UUID or an authorization scope from the client.

The ordinary Projects page remains membership-scoped for every user, including a `super_admin`. Global visibility exists only in the administration endpoint and page.

Each member-list row contains only:

- project UUID, name, optional description, lifecycle status, and update timestamp;
- the membership role projection: built-in key or custom display name.

Built-in role keys are localized by the client. Authorization never depends on the displayed role label.

### Administration project list

`GET /api/administration/projects` first requires an active session and strict `superAdmin === true` server-side authorization. It returns every project with the same safe project fields plus `activeMemberCount`. It does not return membership identities, credentials, documents, audit metadata, or storage details.

The administration UI exposes a Projects tab at `/administration/projects`. An ordinary user cannot load the page or endpoint.

### Project creation

`POST /api/projects` requires an active session, validates a command containing a name and optional description, constructs the actor and audit channel from server-owned session data, and calls the existing shared `createProject` service. The client cannot choose the creator, initial role, permissions, or audit actor.

Project names remain non-unique. Domain failures map to stable safe HTTP responses; PostgreSQL messages and stack traces never leave the server.

## Client feature structure

`app/features/projects` follows the existing Nuxt-native feature boundary:

- `api` owns member-list, administration-list, and creation adapters plus strict unknown-response parsers;
- `model` owns load/create state, pure client-side filtering, status options, role/status/date presentation helpers, and localized safe errors;
- `ui` owns reusable project list controls, table, empty states, loading/error states, and create dialog;
- the feature public `index.ts` exports only page-facing capabilities.

Pages own route composition and select the data scope. The shared `ProjectsTable` accepts typed rows and a mode of `member` or `administration`; it does not decide authorization or fetch data.

## Visual composition

The page follows Figma node `26:84` using semantic design tokens and local shadcn-vue primitives.

- Heading: `Проекты` with the description `Доступные вам рабочие пространства и документация.`
- Primary action: `Создать проект`.
- Controls: project text search and a lifecycle-status selector.
- Member columns: `Проект`, `Описание`, `Ваша роль`, `Статус`, `Обновлён`.
- Administration columns: `Проект`, `Описание`, `Участники`, `Статус`, `Обновлён`.
- Project names are Nuxt links to `/projects/:id`.
- Status uses the local `Badge`; dates use Russian locale-aware formatting.
- The table uses only the installed shadcn-vue Table family rather than hand-built row divs.

Search and status filtering are client-side in this release. Search matches normalized project name or description. Status supports all, active, and archived. The complete accessible result set is loaded because Minerva currently targets a small internal team; pagination is added only when real volume requires it.

## UI states

### Loading and failure

Initial loading renders a table-shaped Skeleton that preserves the page layout. A safe load failure renders a localized Alert and `Повторить` action. Private exception details are never rendered.

### No projects

When the unfiltered API result is empty, render the installed shadcn-vue Empty composition with a project icon, `Проектов пока нет`, supporting text, and `Создать проект`. The same create-dialog action is used by the page heading and Empty CTA.

The administration empty state explains that the system has no projects and also offers creation because any active authenticated user, including a super administrator, may create a project.

### No filter results

When projects exist but active filters match none, render a distinct Empty composition with `Проекты не найдены` and `Сбросить фильтры`. It does not imply that the user has no projects and does not duplicate the create CTA.

### Creation dialog

The installed shadcn-vue Dialog contains a Russian form with required project name and optional description. Client validation mirrors the canonical 120/2000-character bounds for immediate feedback; server validation remains authoritative.

Submission disables duplicate actions and shows a pending label. Success closes the dialog, clears the form, reloads the current scope, and exposes the new project without a page refresh. Failure keeps the entered values and displays a safe localized message. Closing the dialog resets transient errors.

## Data and error flow

1. The page creates scope-specific Projects state and starts loading on mount.
2. The API adapter parses the unknown HTTP response into a readonly typed list or rejects it as an invalid response.
3. Model state exposes pending, safe error, source rows, filter values, and derived visible rows.
4. The page renders Skeleton, Alert, unfiltered Empty, filtered Empty, or ProjectsTable.
5. Creation posts only name and description; on success the state reloads from the authoritative server query.

Network, invalid-response, forbidden, validation, inactive-account, and unavailable-service outcomes map to stable localized UI messages. Raw exceptions remain internal.

## Testing

Unit tests cover:

- strict member/admin response parsers;
- name/description/status filtering and filter reset;
- loading, safe error/retry, unfiltered Empty, filtered Empty, and table component composition;
- mode-specific table columns and project links;
- create-dialog validation, duplicate-submit guard, success reload, and safe failure.

PostgreSQL integration tests cover:

- member list includes only active memberships and does not grant global visibility to `super_admin`;
- removed memberships and inaccessible projects are absent;
- administration list returns all projects and accurate active-member counts only for strict super admins;
- project creation uses the session actor and creates the complete atomic project graph;
- responses contain only the approved safe projection.

Browser tests cover member table rendering, no-project Empty, filtered Empty, successful creation, safe retry after load failure, the administration all-projects tab, and denial of administration access to an ordinary user.

The slice completes only after unit and integration suites, browser journeys, Nuxt type checking, production build, progress update, and Tesserae refresh pass.

## Explicitly deferred

- Server-side pagination, sorting, and search.
- Project update/archive/restore actions.
- Project settings and participant management.
- Custom role editing.
- Documents and credentials UI/data.
- Account anonymization implementation.
